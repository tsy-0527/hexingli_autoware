## 0. 一句话结论

**不是后处理脚本的问题，也不是“一进室内”就必然失败。** 现场实时 FAST-LIO 只跑到 **4.22 Hz**（丢了约 58% 雷达帧），在 **331.3 s 的南北长走廊**先发散；离线用完整 10 Hz 数据重跑后稳定了 12 分钟（681.6 m），最后在 **731.8 s 的下坡/台阶/下层入口**再次发散。**过滤算法只能去动态点/离群点，修不了已经发散的轨迹**；更合适的顺序是先做稳轨迹（分段/回环），再过滤。

## 4. 根因分析

### 4.1 实时性不足（现场发散的主因）

- 雷达 10 Hz，FAST-LIO 只处理 **4.22 Hz**：1051 s 内 `/Odometry`/`/cloud_registered` 各 4436 帧，而 `/livox/lidar` 10512 帧。
- 相邻处理帧间隔从 0.1 s 变成约 0.24 s；车辆 0.5–0.8 m/s 时，两帧间移动 0.12–0.19 m。
- 现场同时运行：RViz、`dense_publish_en: true`、`map_en: true`、`scan_bodyframe_pub_en: true`、7 个话题录包、Livox 驱动；FAST-LIO 主线程平均约 67%，实时跟不上。
- 离线 `rviz:=false` + 0.5x 回放 + `ROS_LOCALHOST_ONLY=1` 能到 10 Hz，并稳定 12 分钟——**数据本身没问题，差的是现场处理余量**。
- 这解释了为什么现场在 **331.3 s** 就发散，而离线能撑到 **731.8 s**。

### 4.2 几何退化（离线发散的主因）

**长走廊：沿走廊方向没有约束**

- 南北长走廊两侧是平行墙，点面匹配只能约束 x/z，沿 y 方向退化。
- 现场 4.22 Hz 下，帧间位移更大，ICP 更容易滑；最终在长走廊里出现 59.8 m 跳变。

**台阶/坡道：地面平面突变**

- 轨迹在 660 s 后从 z=0.759 m 降到 690 s 的 -0.980 m、720 s 的 -3.230 m，说明车辆在下坡/进入下层。
- 台阶边缘的 5 个最近邻点可能跨两个高度层；`esti_plane`（阈值 0.1 m）无法拟合出单一平面 → 该帧没有有效点。
- 匹配恢复时，可能锁到下层地面/错误楼层，z 直接跳变。

**`No Effective Points!` 的代码含义**

`/home/tang/fastlio_ws/src/laserMapping.cpp:772`：

```cpp
if (effct_feat_num < 1) {
    ekfom_data.valid = false;
    std::cerr << "No Effective Points!" << std::endl;
    return;
}
```

- 当前帧没有任何点找到有效地图平面（5 个最近邻、距离 <2.24 m、平面残差 <0.1 m、s>0.9）。
- `ekfom_data.valid=false` → **EKF 的雷达更新被跳过**，位姿只靠 IMU 递推。
- IMU 有零偏/噪声；连续多帧没有雷达约束就会漂；等下一帧匹配上时可能匹配到错误位置/楼层，产生几十米跳变。
- 恢复日志 **2338/8913 = 26.2%** 的帧出现该提示，说明不只是台阶，长走廊/大空场也在持续退化。

**IMU 是正常的**

- 680–760 s：26000 条 IMU / 130 s = 200 Hz；中位 dt 4.9 ms；最大间隔 6.3 ms。
- 加速度范数 0.21–5.95 m/s²；角速度最大 2.56 rad/s；没有 >5 rad/s 的饱和。
- 所以发散不是 IMU 丢帧/饱和，而是**几何约束不足 + 平面误匹配**。

### 4.3 录制时长与无回环

- 17.5 min / 7.5 GB 在工具建议的 45–60 min 以内，**不是“超时”问题**。
- 但 FAST-LIO2 没有回环；12 min / 681.6 m 的轨迹已经有累积误差；地图/ikd-Tree 增大、CPU 变慢，会进一步降低现场帧率。
- **结论：时长是诱因，不是直接原因。** 每段 10–15 min、在台阶/楼层处分段更稳。

### 4.4 “断网导致丢数据”排查

- 原始 bag 的 `/livox/lidar` 和 `/livox/imu` 计数精确到 10/200 Hz，**没有丢帧**。
- 现场 4.22 Hz 是 FAST-LIO 的处理/接收能力，不是录包丢数据。
- 离线用 `ROS_LOCALHOST_ONLY=1`、关 RViz、0.5x 回放能到 10 Hz 并稳定 12 min，证明数据本身可用。
- 如果现场 DDS 走 Wi-Fi/复杂网络，建议固定 `ROS_LOCALHOST_ONLY=1` 和 `ROS_DOMAIN_ID`，或只录原始数据离线重建。

### 4.5 台阶/坡道的影响

- **影响很大，是离线重跑的直接触发点。**
- 660 s 后 z 从 0.759 m 降到 -3.230 m（720 s），说明车辆在下坡/进入下层。
- 台阶边缘的平面拟合失败 → `No Effective Points!` → 跳过雷达更新 → IMU 递推 → 锁到错误楼层 → z 跳变。
- 这一段 IMU 正常（200 Hz、无丢帧、无饱和），所以不是 IMU 问题。
- **台阶不是不能建图，而是不能一段连续建。** 台阶前后各加 10 s 静止、分段重跑即可。

### 4.6 脚本/数据突变排查

- **不是后处理脚本的问题。** `mapclean` 在有效数据上结果正常：地面残差 1.7 cm、雷达离地中位数 0.581 m（配置 0.57 m，偏差 1.1 cm）。
- **也不是“室外→室内”这个动作本身。** 现场第一次发散在长走廊（331.3 s），离线在台阶（731.8 s）。
- 真正的数据问题是 `/Odometry` 已经发散；`/cloud_registered` 用同一个位姿生成，所以点云地图一起坏。
- 离线重跑在同一份原始数据上重新算了一条 `/Odometry`，所以 0–731 s 是好的。

## 6. 为什么“先建图再过滤”不能解决这次问题

- DUFOMap 解决的是**动态点/残影**；mapclean 解决的是**地面下反射、离群点、车道路径残影**。
- 它们都默认：**输入点云已经在几何上自洽**。
- 本次 `/Odometry` 在 331.3 s 出现 59.8 m 跳变，`/cloud_registered` 用同一个位姿生成，所以点云已经出现**错层、重影、墙体拉长**；任何过滤算法都无法判断哪一层是真的。
- 过滤能做的：
  - 动态：DUFOMap（已用）；ERASOR / Removert 可补充；
  - 地面/坡道：Patchwork++ 或局部地面切片；
  - 离群/残影：SOR / ROR + route_check（已用）；
  - 玻璃/镜面：雷达穿透，算法难补，**CloudCompare 手动补墙/删点**。
- 过滤不能做的：
  - 修 59.8 m 跳变、重影、错层；
  - 修台阶处的楼层误匹配；
  - 修长走廊的累积漂移。
- **结论：过滤要建立在“轨迹正确”之上。** 本项目当前的一层图在有效段已经过滤得不错；要提升，优先做轨迹（分段/回环），而不是继续加滤波器。

**2D 栅格的特殊问题：**

- 当前 `make_grids` 用**全局绝对高度切片**（0.05–2.0 m）。
- 场地有约 0.7 m 的高差/坡道；抬高走廊的地面落在切片内，会被当成障碍，导致 565 个轨迹位姿落在“占用格”。
- 这不是 3D 图错误，是 2D 表达方式不适合多层/坡道；应改用**按层切片**、**局部地面高度切片**，或直接用 SLAM Toolbox 的 2D 图。

## 7. 更合适的建图方案

### 7.1 方案 A：SLAM Toolbox 2D + 3D 聚合（单层最稳，推荐一层）

本机已装 `slam_toolbox`（含 `offline_launch.py`）、`pointcloud_to_laserscan`、`nav2`、`pcl_ros`，可以零新依赖实现：

1. `pointcloud_to_laserscan` 把 MID360S 的**离地 0.3–1.5 m 切片**转成 `/scan`：
   - `target_frame: livox_frame`
   - `min_height: -0.35`、`max_height: 0.90`（相对雷达；雷达离地 0.57 m）
   - `angle_min/max: -π/π`、`angle_increment: 0.0087`、`range_max: 30`
2. 补一个静态 TF `odom → livox_frame`（identity）；`slam_toolbox` 用：
   - `map_frame: map`、`odom_frame: odom`、`base_frame: livox_frame`
   - `scan_topic: /scan`、`mode: mapping`、`resolution: 0.05`
   - `do_loop_closing: true`
3. `slam_toolbox` 输出带**回环闭合**的 2D 图和 `map → livox_frame` 位姿。
4. 用回环后的 `map → livox_frame` 把原始 `/livox/lidar` 聚合回 3D PCD（单层 z 固定），再走 DUFOMap + mapclean。

**优点：**

- 长走廊/大回环比 FAST-LIO 稳，**有回环**；
- 2D 图可直接给 Nav2；
- 不依赖 IMU，不会出现 `/Odometry` 突然爆掉；
- 本机零新依赖（只需补 TF 和参数）。

**缺点：**

- 单层假设；台阶/下层要分段；
- 3D PCD 的 z 固定，坡道/多层不适用；
- 需要写“用 TF 聚合 3D 点云”的脚本。

### 7.2 方案 B：GLIM（多层/整栋 3D，推荐完整 3D 图）

- 本机 **RTX 3060 Laptop 12 GB**，CUDA 可用；GLIM 的 GPU 扩展可跑。
- ROS2 原生，支持 Livox + IMU，**全局优化 + 回环**。
- 适合整栋/多层/长走廊，直接输出 3D PCD，不需要 2D 切片。
- 缺点：需要安装/编译/配置（GTSAM、CUDA 扩展等），比 FAST-LIO 重；本机目前没装。

### 7.3 方案 C：分段 FAST-LIO + DUFOMap + mapclean（最小改动，当前）

- 一层主体 `--duration 660`；下层单独 `--start 680`；
- 每段用 `quality_report.md` 门控；
- 已实现，不装新东西。
- 优点：每层图干净、可控；缺点：无回环，长走廊有漂移；每层是单独图。

### 7.4 不推荐

- **LIO-SAM**：需要 9 轴 IMU/GPS，本机 Livox IMU 是 6 轴；
- **Point-LIO**：没有回环，解决不了长走廊漂移；
- **Cartographer**：本机没装，3D 支持一般；
- **纯 2D SLAM 直接当 3D 图**：z 固定，台阶/坡道不行。

### 7.5 选择建议

| 目标 | 推荐 | 原因 |
|---|---|---|
| 一层 Nav2 + 3D NDT | **A（SLAM Toolbox 2D + 3D 聚合）** | 已装、有回环、2D 图直接可用 |
| 整栋/多层一张 3D 图 | **B（GLIM）** | GPU 可用，全局优化/回环 |
| 快速交付、每层单独图 | **C（分段 FAST-LIO）** | 已实现，风险最低 |
| 只想去动态/离群 | DUFOMap + mapclean | 不能修轨迹 |

**本项目建议：**

- **一层用 A**；台阶/下层用 **C**；如果要整栋一张 3D 图再上 **B**。
- 当前这版 0–731 s 的一层图可以作为 baseline；重跑 `--duration 660` 会明显改善 z 波动和 1.14 m 跳变。
